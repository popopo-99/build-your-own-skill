# Skill Canvas：把对话整理成可构建的设计

Skill Canvas 是系统从对话中整理出的设计摘要，不是要求用户逐项填写的申请表。先自动填充已有信息，只询问会实质改变 Skill 的缺口。

## 字段

### PURPOSE

第一版解决的具体问题，以及它为什么值得重复执行。

### USER

直接使用者、他们的熟练程度和使用场景。

### INPUT

可靠完成任务所必需的输入。标明可接受的形式，例如自然语言 Brief、图片或现有文件。

### OPTIONAL INPUT

能改善结果但不是必需的信息。说明缺失时采用什么假设或降级方式。

### ANALYZE

执行前要观察和理解什么，例如品牌阶段、受众、限制条件和素材完整度。

### DECISION

分析结果如何改变后续做法。尽量写成“如果……则……”的可执行规则。

### WORKFLOW

用户真实工作的步骤、分支与循环，而不是为了完整而套用固定框架。

### KNOWLEDGE

AI 需要按需读取的专业判断、例外、失败经验、Checklist 或标准。优先用户独有的隐性知识。

### ROUTER

仅当不同任务类型确实进入不同流程时使用。写清路由信号和对应流程；否则写“不需要”。

### CONSTRAINTS

- **Hard Constraints**：永远不能违反；
- **Preferences**：优先遵守，但可因上下文调整。

### OUTPUT

最终交付物的结构、数量、字段、格式和必要解释。

### CHECK

如何检查约束、完整性、可执行性、一致性、事实依据与输出格式。

### REPAIR

检查失败时，如何定位问题、修复并再次检查。

### TOOLS

只有任务需要最新信息、确定性计算、文件处理或外部系统时才加入，并写清触发条件与失败处理。

### TEST

用哪些代表性输入证明 Trigger、Workflow、Constraints 和 Output 可用。

## 从对话自动填充

1. 提取用户明确说出的事实，不改写成更宏大的目标。
2. 从真实案例推断 User、Input、Workflow 和质量标准。
3. 把推断标为“暂定”，不要伪装成用户已确认。
4. 把不知道但不影响当前设计的字段标为“V0.1 暂不需要”。
5. 只对高影响空缺提出 1–3 个问题。
6. 更新 Canvas 时保留已确认内容，避免反复询问。

例如，用户说“我主要帮餐厅拍菜单和宣传照，每次都先按融化速度排菜品顺序”，可以直接推断：

- User：餐厅摄影师或小型创意团队；
- Purpose：规划餐厅食品摄影；
- Analyze：菜品状态变化、出餐节奏和用途；
- Decision：优先拍摄状态窗口最短的菜品；
- Knowledge：用户判断最佳拍摄窗口的经验。

不应再问“你的 Skill 用户是谁？”这种答案已明显的问题。

## 从 Canvas 到文件

- Purpose、触发、主流程、关键约束和资源路由进入 `SKILL.md`；
- 大量专业规则进入 `references/`；
- 可复制的结构化产物进入 `templates/` 或 `assets/`；
- 只有重复且要求确定性的操作进入 `scripts/`；
- 代表性输入与预期行为进入 `tests/`。

Canvas 不是最终产品。若某字段不会改变执行方式，就不要为了“填满”而添加空泛内容。
