# Deep Discovery

## Purpose

深度发现不是增加提问数量，而是把隐藏的需求、矛盾和关键判断变成可执行的 Skill 设计。帮助用户作出自己的决定，不代替用户发明一套方法。

## Quick vs Deep / When to Enter

[Quick Discovery](discovery.md) 是默认起点。一般想法先从近期真实案例问起，信息足够就设计，不要求用户接受长访谈。

- 用户明确说“多问问我”“深挖一下”“采访我”“challenge 我”“帮我想清楚”“我自己也不知道真正想做什么”“帮我把需求问明白”时，可进入 Deep。
- Quick 已进行少量轮次，仍有会根本改变 Scope / Workflow 的缺口时，先指出具体缺口，再建议：“这里还有几个会直接改变 Skill 设计的关键决策。如果你愿意，我可以进入 Deep Discovery，把它们逐步问清楚。”得到同意才切换。
- 用户可以拒绝、收窄范围、要求一次一问或结束深访。拒绝后回到 Quick 或交付带明确假设的候选设计；不能假装缺口已经解决。
- 已有清晰设计、只需导入材料或修复具体故障时，不强制重做深访。Deep 默认 READ / DESIGN；访谈同意绝不是 Build 授权。

## Decision Frontier

决策前沿（Decision Frontier）是**现在有条件诚实作答的问题集合**：问题依赖的前置决定已经足够明确。它不是要展示给用户的完整决策树，也不是固定问卷。

每轮先在内部判断依赖关系。例如：服务“活动主办方”还是“现场设计师”尚未确定时，先问使用者和使用时刻；不要先问最终交付有几个模块。即使两个问题都重要，若后一个依赖前一个的回答，也不能放在同一轮。

前沿是可修正的判断：用户改变上游决定时，重新检查依赖它的结论，指出哪些失效；不要为维持旧方案而忽略新证据。

## Question Value

只保留答案会影响第一版的问题，至少能改变 Scope、Workflow、Hard Constraint、关键决策规则、Output 或测试标准，或能暴露失败模式、隐藏假设、矛盾。

例如，问“什么现场限制会直接否掉方案？”可能改变硬约束；问“以后要不要十种导出主题？”若不会改变当前 V0.1，就暂缓。不要因为 Canvas 有空格而提问。

## Uncertainty Types：Grillable / Researchable / Testable / Deferrable

先判断缺口需要哪种证据，再选择动作，不把所有未知都交给用户。

| 类型 | 判断依据 | 动作 |
| --- | --- | --- |
| USER-ANSWERABLE | 答案在用户经验、偏好或取舍中，例如为什么否决一个方案 | Ask：从真实案例、反例或比较中追问 |
| RESEARCHABLE | 依赖外部事实，例如当前市场、API 能力、平台规则或趋势 | 有合适工具时 Research，记录来源与适用时间；无工具或研究失败时标记 Requires Validation，不让用户猜事实 |
| TESTABLE / PROTOTYPABLE | 谈话不能可靠判定体验、视觉效果、稳定性或流程负担 | 执行下方 Testable Exit Rule，退出该决策的访谈并交接最小 Prototype / Evaluation，不再靠追问选择方案 |
| LOW-IMPACT / DEFERRABLE | 不影响第一版的低优先偏好 | Defer，或明确说明临时默认及以后重新决定的条件 |

用户说“不知道”时先判断答案需要哪种证据，不能一律转 Prototype。若答案在用户真实经验、工作习惯或取舍中，仍属 USER-ANSWERABLE，可以追问依据。混合问题可拆开，例如“平台是否允许”需要研究，“允许后愿不愿意采用”才是用户决定。

Research 只能在现有工具、隐私和任务边界内进行，不能为查事实擅自注册服务或修改外部系统。Prototype 是建议，不自动授权生成文件；实际执行仍受 [SKILL.md 的 Write Gate](../SKILL.md) 约束。暂时无法验证的重要前提应保留为阻塞或条件假设，不假装设计已定案。

### Testable Exit Rule

本节说明 Deep Discovery 如何识别并交接 TESTABLE 决策，也可由其他模式直接读取。[全局 Evidence Boundary](../SKILL.md#evidence-boundary全局证据边界) 由 SKILL.md 定义：一旦识别为 TESTABLE，中立性立即生效；最小测试条件只决定立即 Handoff 还是最多补一轮条件，不决定中立性是否生效。

当以下条件同时满足，该决策必须退出 Discovery，转入 Prototype / Evaluation Handoff：

1. 用户无法凭已有经验直接判断哪个候选方案实际更好；
2. 候选方案各有合理优点和已知失败风险；
3. 真实使用场景已可描述；
4. 已能从现有目标与失败模式中提取至少 2–3 个比较标准；
5. 再问只能细化候选设计，不能提供可靠的选择证据。

识别为 TESTABLE / PROTOTYPABLE 后，不再通过访谈尝试选出赢家。先复用已有上下文提取测试条件，不要求用户把已经说明的目标重新表述成 criteria。

- 使用场景与基本比较标准已经足够：本轮直接 Handoff，零追加澄清。
- 仍有必要缺口：对同一决策最多再问一轮、1–3 个最小测试条件问题，仅补 real use case、what success means、known failure modes、comparison criteria。已进行过的这一轮计入上限，不能换措辞或换标签重新计数。
- 一轮后仍有缺口：停止该决策的访谈，交接已知条件与待补证据，标记尚未具备执行条件；不编造标准或宣布某方案胜出。

不能继续询问更细的内容结构、更多输出字段、设计细节、风格偏好或如何优化候选内部内容，把它们当作延长 Discovery 的理由。这些属于后续 Prototype / Design；交接不意味着已执行测试，也不意味着所有其他 USER-ANSWERABLE 决策都要停止询问。

### Prototype / Evaluation Handoff

明确输出 **TESTABLE DECISION**，然后交付：

- **What we know**：按候选总结用户已提供的优点和失败风险，明确 USER-DERIVED 来源，不转成推荐排序。
- **What we do not know**：明确哪一种在真实使用中更好仍未知。
- **Why reasoning stops**：说明该决策已停止追问；继续推理可以产生假设，但不能可靠判断真实使用效果，缺少的是实际 Evaluation evidence。
- **Minimum Prototype**：计划对同一个真实输入制作最小 A/B 样例，保持内容、任务和其他条件一致，只比较待定变量；若提出新候选或理论猜测，分别标为 **PROPOSED CANDIDATE** 或 **HYPOTHESIS**，沿用全局证据边界。详细比较方法按需阅读 [evaluation.md](evaluation.md)。
- **Compare on**：从用户已给目标和失败模式提取最少必要标准；额外建议的标准明确标为 PROPOSED，不冒充用户原有判断。
- **Current Status**：未获实际运行授权或本轮只设计方案时，必须写 **Not Executed** 和 **No winner selected**；不创建文件、不运行 A/B、不选择赢家。后续执行继续遵守 Write Gate。

例如，真实 Brief 保持相同，Version A 为“核心概念 → 视觉 / 玩法 / 执行”，Version B 为“视觉 / 体验 → 核心概念总结”。若用户已说明希望设计师既理解主线又立即动手，可据此比较：能否复述方向为什么成立、能否开始找参考 / Moodboard / 构图草图、是否仍出现“讲得通但画不出”或“细节多但抓不住主线”。若三方向差异也是用户已有目标，再检查是否容易区分，不把示例变成所有任务的固定量表。

## Asking in Rounds

1. 简短汇总已知事实和已确认决定，优先复用已有上下文，不重复问已回答内容。
2. 找出对第一版影响最大的不确定性，并按证据类型分类；TESTABLE 优先执行退出规则，不继续进入常规提问循环。
3. 检查前置条件，移除当前不能诚实回答的下游问题。
4. 从当前前沿中选择最高价值的 1–3 个问题；问题间不能互相依赖，也不能在一个编号内塞入十个子问题。
5. 使用用户职业语言，必要时解释为什么这个决定会改变设计。不要求用户填写 YAML、Router 或整张 Canvas。
6. 根据回答更新理解与来源，重新计算下一轮；每轮都检查是否应停止或转研究 / 实验。

对 USER-ANSWERABLE 决策，可以推荐选项，但须明确它是系统建议，不用推荐答案诱导用户一路“同意”；TESTABLE / PROTOTYPABLE 决策遵守全局 Evidence Boundary，不得用这条提问规则绕过。用户的模糊同意不能覆盖尚未解决的矛盾，更不能开启文件写入。

## Challenge Patterns

挑战针对具体证据和取舍，不针对用户本人，也不为辩论而辩论：

- 目标冲突：“你希望完全标准化，又希望每次自由发挥；在哪个环节分别优先？”
- 规则与案例不符：“刚才这次没有先做调研。什么条件让你跳过它？”
- 必要性检查：“去掉这一步后，哪一种可观察的错误会增加？”
- 习惯与依据：“这一步依靠什么信号判断有效？还是目前沿用的习惯？”
- 反例检查：“什么结果即使看起来完整，你也不会交付？”

允许用户说明例外、否定建议或修正问题前提。不要把一次例外强行升级成全局规则，也不要只复述并附和用户。

## Knowledge Provenance

沿用入口的来源规则：USER-DERIVED 是用户明确提供的经验和判断；INFERRED 是从案例推导的结论；PROPOSED 是系统补充建议。

重要推断要说明依据和不确定性。访谈中提出的新框架若将成为 Hard Constraint、核心 Workflow、Router 或核心评价标准，正式纳入前必须向用户披露其 PROPOSED 来源；不能经过几轮对话就改称“你的方法”。用户可以采纳建议，但采纳不会改变它的来源。最终 Skill 不要求展示这些标签。

## Stop Conditions

没有固定总问题数，也不以“问够 20 个问题”为目标。以下信息已足够支持第一版，且后续提问不会实质改变它时，停止：

- V0.1 Scope 可描述，主要输入与使用者清楚；
- 核心 Workflow 能执行，关键分支能解释；
- Hard Constraints 足够明确；
- 有真实案例中的成功或失败判断，Output 可验证；
- 剩余未知已归为 Researchable、Testable 或 Low-impact，不再是可通过访谈解决的关键决策。

如果关键答案依赖研究或原型，停止的是访谈，不是宣布所有需求已验证。可以交接带条件的设计；受阻部分保持待验证。用户要求提前停止时，给出现有理解与风险，不继续盘问。

## Handoff to Design

用简短交接交付，不要求用户重新填写内容：

- **Current Understanding**：问题、用户、场景与依据。
- **Key Decisions**：范围、流程、关键分支、约束与检查；重要推断 / 建议标明来源。
- **Remaining Unknowns**：未决问题及影响，不把未知写成事实。
- **What needs Research / Prototype**：需要什么证据、最小验证动作；无此类问题就说明无。
- **Candidate Skill Statement**：当谁需要什么，通过什么方法得到什么结果。
- **下一步建议**：进入 Design，沿用已有信息形成 Canvas / Build Proposal；未获明确授权不 Build。

## Failure Modes

- 认为问题越多越好，一次问十几个问题或输出整棵决策树。
- 在用户类型未定时追问下游输出细节。
- 用户已经回答还重复问，或强迫普通用户接受 Deep。
- 把 Research 问题甩给用户猜；工具失败却声称事实已核实。
- 把需要 Prototype 的问题无限讨论，或擅自创建原型文件。
- 测试条件已够仍追问候选结构与风格，或把“一轮最小澄清”不断重置；反过来把所有“不知道”都误判为 TESTABLE。
- 只确认用户观点而不检查明显矛盾，或反过来为了挑战而争辩。
- 把系统方法冒充用户经验；用模糊“继续”越过 Write Gate。
- 信息足够仍不停止，或把仍待验证的重大前提藏在最终设计中。
