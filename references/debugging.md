# Skill Doctor：定位后再修复

当 Skill 表现不好时，不要先重写全部文件，也不要不断在 `SKILL.md` 末尾追加新 Prompt。先把可观察问题归到负责的模块。

## 诊断流程

`AUDIT → PROBLEM → ROOT CAUSE → MINIMUM CHANGE → TEST`

1. 保存导致失败的原始输入和实际输出；
2. 写出一个可观察的问题，不用“感觉不好”概括；
3. 定位最早发生错误的模块；
4. 做能解释该根因的最小修改；
5. 重测失败用例与相邻正常用例。

## 症状与常见根因

| 症状 | 优先检查 | 典型修复 |
| --- | --- | --- |
| Skill 没触发 | `description` / Trigger | 用用户会说的任务语言说明何时使用，去掉空泛营销词 |
| 不相关请求也触发 | `description` / Boundary | 缩小触发范围，写清相邻但不属于的任务 |
| 一上来问很多问题 | Discovery / Conversation UX | 先提取已有信息，每轮只问最高影响缺口 |
| 结果太泛 | Workflow / Knowledge | 补真实决策规则、案例差异和专业检查 |
| 不遵守要求 | Constraints | 区分硬约束和偏好，增加输出前检查 |
| 格式不稳定 | Output | 明确数量、字段、顺序和缺失处理 |
| 只改一项却全变 | One Variable Rule | 显式列出修改变量与锁定变量并逐项检查 |
| 多个方向高度重复 | Differentiation Rules | 指定必须不同的核心维度并增加重复检查 |
| 走错流程 | Router | 改善路由信号与默认分支，删除无意义模式 |
| 文件越来越臃肿 | Progressive Disclosure | 把条件知识移到单一职责 reference，删除重复 |
| 工具失败仍声称成功 | Tool Failure | 显式处理错误、重试边界和降级输出 |

## 找到最早的错误

最终输出格式错误不一定属于 Output。如果上游分析遗漏关键信号，即使格式正确也会产生错误结果。按顺序检查：

1. 是否正确触发和路由；
2. 是否获得必要输入；
3. 是否执行正确分析和决策；
4. 是否使用了适用的专业知识；
5. 是否遵守约束；
6. 是否按约定输出；
7. Check 是否发现问题；
8. Repair 是否真的修复。

## 最小修改原则

- Trigger 问题优先改 description，不重写领域知识；
- 知识不足只补有证据的规则，不增加泛化形容词；
- 格式问题修改 Output 和 Check，不重排整个 Workflow；
- 单个坏案例不自动升级为全局绝对规则；
- 移动内容前检查所有引用，避免断链和重复。

## 防止 Prompt Spaghetti

出现互相覆盖的“始终”“除非”“但是”时，先合并冲突规则并决定优先级。删除被替代的旧规则，不把新要求简单追加到底部。

每次修复记录：失败用例、根因、修改模块、回归结果和版本。若无法稳定复现，先补测试或观察，不假装已经定位。
