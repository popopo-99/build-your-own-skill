# Architecture：选择最小必要结构

架构的目标是让 Skill 稳定工作，而不是展示复杂度。每增加一个目录、Router、脚本或工具，都应解决已经出现的真实问题。

## 成熟度模型

| Level | 结构 | 适用情况 |
| --- | --- | --- |
| 0 | Prompt | 一次性、低风险、无需维护的任务 |
| 1 | 单一 `SKILL.md` | 一个清晰问题，规则和流程不长 |
| 2 | Workflow + Rules | 有稳定步骤、分支和约束 |
| 3 | References + Templates | 详细知识或可复制产物需要按需使用 |
| 4 | Router + Check + Repair | 多类任务使用不同流程，且需自检修复 |
| 5 | Scripts + Tools | 需要确定性处理、外部信息或系统操作 |
| 6 | Tests + Versioning | 需要稳定维护、回归检查和发布记录 |
| 7 | Composable Skill System | 多个成熟能力确有复用与组合需求 |

Level 不是质量等级。一个边界清晰的 Level 1 可能优于臃肿的 Level 5。

## 文件职责

### `SKILL.md`

编排层：Purpose、Trigger、主流程、关键判断、硬约束、资源路由、Check/Repair 和完成条件。保持可快速读取。

### `references/`

按需读取的详细知识：领域规则、模式专用流程、数据结构或深度指南。每份文件有清晰职责，并由入口说明读取条件。

### `templates/` 或 `assets/`

用户或 Skill 会复制、填写、改造的产物。模板属于可交付材料，不应被当作核心指令全文加载。

### `examples/`

用于解释结构或对照结果的真实案例。案例不能悄悄成为所有任务的默认规则。

### `scripts/`

只用于重复、确定性且纯文字指令难以稳定完成的操作，例如批处理、验证、数据转换或文件生成。新增后必须实际运行验证。

### `tests/`

保存代表性输入、预期行为和失败信号。重点验证决策，不只匹配固定措辞。

## 渐进式披露（Progressive Disclosure）

信息分三层出现：

1. `name` 与 `description` 决定是否加载 Skill；
2. `SKILL.md` 决定本次任务采用什么流程；
3. references 只在对应阶段或模式被读取。

如果每次都必须读取所有 references，拆分可能没有价值。如果 `SKILL.md` 反复复制 reference 内容，边界也已经失效。

## Router 判断

只有当输入信号能可靠区分至少两条实质不同的流程时才增加 Router。

合理示例：

- 新想法 → Discovery；
- 现有 `SKILL.md` → Review；
- 明确单变量修改 → Remix / One Variable Rule。

不合理示例：为了命名漂亮，把同一线性流程分成五个模式。

Router 必须说明：识别信号、进入的流程、信息不明确时的默认行为，以及冲突时如何处理。

## Constraints 与 One Variable Rule

- **Hard Constraints** 优先于偏好和美化；冲突无法消解时，说明冲突并请求关键决定。
- **Preferences** 可以根据上下文权衡，权衡后说明重要偏离。
- 当用户明确“只改一个变量”时，先列出被修改变量和被锁定变量；输出前检查构图、身份、结构、风格等锁定项是否意外变化。

## 何时增加复杂度

增加结构前需要对应证据：

- `references/`：入口文件因条件知识过长而难以导航；
- Router：同一入口出现两条以上不同流程；
- template：同一种结构反复交付；
- script：相同确定性操作被反复手写且容易出错；
- tool：任务需要最新信息、计算、文件或外部系统；
- 更多测试：观察到新的失败模式或兼容场景。

不要因为“以后可能需要”提前加入。

## Build Proposal

构建前给出简短提案：

1. V0.1 解决的问题；
2. 计划创建或修改的文件；
3. 每个文件的职责；
4. 不加入的复杂度及理由；
5. 验证方式。

若用户已明确授权构建且设计信息完整，提案可以与实施连续进行，不必额外等待确认。
